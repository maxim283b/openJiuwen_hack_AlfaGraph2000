# AlfaGraph2000 — openJiuwen Challenge 2026

Агент на openJiuwen. Выбирает задачи и прогнозирует оставшийся расход токенов.
Использует разрешённые модели через API организаторов.
Выбирает ответы для независимой проверки по прогнозу пользы и стоимости в пределах общего бюджета.

## Запуск

```bash
docker build -t alfagraph2000 .
export LLM_API_KEY='ваш-ключ'
docker run --rm --read-only --tmpfs /tmp:rw,size=2g \
  --cpus 4 --memory 16g \
  -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET=100000 \
  -v /absolute/path/to/tasks:/data/tasks:rw \
  alfagraph2000 --tasks-dir /data/tasks
```

Вход: каталоги задач с `task.json` и `workspace/`.
Ответ: `answer.txt` рядом с `task.json`; исправления coding — в `workspace/`.
Для невыполнимых задач файл ответа не создаётся.
Отчёт и траектории: `TASKS/.harness/`.
Поддерживается запуск с `--entrypoint python IMAGE /app/run_agent.py --tasks-dir /data/tasks`.
Для продолжения прерванного запуска используйте `--resume`, сохранив прежний отчёт расхода.

Параметры:

- `LLM_API_KEY` — ключ API; передаётся только при запуске.
- `LLM_BASE_URL` — по умолчанию `https://api.neuraldeep.ru/v1`.
- `BUDGET` — общий бюджет; 10 входных токенов равны одному выходному.
- `AGENT_CONCURRENCY` — в Docker 2, максимум 5.
- `AGENT_RPM` — в Docker 45 запросов в минуту.
- `AGENT_VERIFICATION` — в Docker включена (`1`); `0` отключает независимую проверку.
- `AGENT_REVIEW_STRATEGY` — в этой ветке Docker использует `search_only`: проверяются
  search по награде, остальные кандидаты сохраняются. `learned` включает обученный выбор.

Зависимости закреплены в `requirements.lock`, тег базового образа — в `Dockerfile`.
Локальные веса LLM не нужны.
`--offline` запускает только локальные решатели.

## Планирование и бюджет

Каждая задача проходит workflow openJiuwen: локальный решатель, LLM, проверка, сохранение.
Контекстный бандит выбирает модель и лимит по типу и признакам сложности задачи.
Очередь `density` выбирает следующий шаг по отношению ожидаемых баллов к оставшимся
затратам. Прогноз учитывает размер данных, структуру кода, уже потраченные токены,
чтения, изменения файлов, ошибки и результаты инструментов. Состояние задачи между
шагами сохраняется; у каждой задачи есть индивидуальный потолок расхода.

Общий расход: `prompt_tokens / 10 + completion_tokens`; reasoning уже входит в completion,
кешированные входные токены не вычитаются. До каждого запроса резервируется бюджет
с учётом параллельных вызовов. После ответа резерв заменяется фактическим usage;
если usage отсутствует, списывается весь резерв. Проверка ответов оплачивается
из того же бюджета. При равенстве баллов меньший расход выгоднее.

## Невыполнимые задачи и проверка

Локальные решатели и LLM проверяют наличие необходимых значений и противоречия.
Независимая проверка search сверяет предпосылки вопроса и цитаты из файлов;
числовые ответы пересчитываются Python, coding проверяется исходными и дополнительными
тестами. Исходные тесты изменять нельзя. При установленном недостатке данных ответ
не сохраняется. Сбой или нехватка бюджета проверки сохраняет исходный кандидат
как непроверенный; это не означает, что задача невыполнима.

## Собранные траектории

Для обучения использованы открытые GSM8K, SQuAD2, WikiSQL и MBPP. Маршрутизатор обучен
на 192 API-пробах для 64 задач с разными моделями и лимитами. Прогноз продолжения построен
по 276 подходящим траекториям и 345 состояниям; обучение и внутренняя проверка разделены
по группам источников. Правильность определял внешний оценщик, эталоны агенту не передаются.
В `profiles/` включены готовые профили стоимости, бандита и прогноза; исходные наборы
и журналы экспериментов для запуска не нужны. Во время работы ничего не скачивается.

Новые траектории пишутся в `.harness/trajectories.jsonl`: модель, вызовы инструментов,
затраты, прогресс и результаты проверки. Сводный расход и статусы — в `.harness/report.json`.
Ключи API и полные промпты в эти журналы не записываются.

## Выбор проверок

Для `AGENT_REVIEW_STRATEGY=learned` переменная `AGENT_REVIEW_POLICY` указывает на
`profiles/review-expanded-20261108.json` (путь задан в Docker).
Три линейных прогноза оценивают исправление, ухудшение и расход проверки. Используются
57 признаков условия, кода, таблиц и прогресса, а также TF-IDF со словарём из 512
текстовых признаков, выделенных только на обучении. Очередь выбирает положительный
ожидаемый прирост баллов на токен с учётом оставшегося бюджета. Эталоны и ID задач
в признаки не входят. Runtime использует стандартную библиотеку Python.

Обучение: 196 проверок на SVAMP, FinQA, BigCodeBench, HotpotQA и SQuAD2;
9 улучшений, 0 ухудшений. Вред ограничен априорным минимумом 1%.
На новом наборе из 100 задач с одинаковыми исходными решениями и лимитом 100К:
173/235 за 81,9К против 167/235 за 99,6К у предыдущей версии.
Это один прогон; преимущество над простым выбором только поисковых проверок
не установлено. Ответов на нерешаемые задачи стало больше: 10 против 4.

На следующем наборе из 100 задач поисковая очередь дала 183/228 за 68,3К,
обученная — 178/228 за 78,1К. Поэтому в этой ветке выбран простой режим;
прогноз сложности и стоимости решения задач продолжает работать.
Подробности и ограничения сравнения — в журнале ниже.

Невыбранные ответы сохраняются. `-e AGENT_REVIEW_STRATEGY=learned -e AGENT_REVIEW_POLICY=`
возвращает фиксированный порядок всех проверок; `-e AGENT_VERIFICATION=0`
отключает независимую проверку полностью.

Ход экспериментов, контрольные сравнения и ограничения: [EXPERIMENTS.md](EXPERIMENTS.md).
В этой ветке дополнительно исправлена обработка противоречивых coding-вердиктов:
невалидные дополнительные тесты сохраняют исходный ответ, а ремонт требует
явного подтверждения валидности тестов. Результаты новой проверки — в разделе 21 журнала.
